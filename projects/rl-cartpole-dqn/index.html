CartPole: from a hand-written rule to a learned policy

CartPole is an inverted pendulum — the textbook control problem — dressed up as an RL benchmark. That makes it the right place to ask a question I actually care about: what does learning give you that a designed controller doesn't?

Three agents, one environment

Rather than jumping straight to a DQN, I built up in three steps so that each one had something to be compared against.

The rule-based controller matters most here. It's easy to be impressed by an RL agent balancing a pole until you write twenty lines that push the cart in the direction the pole is falling and watch that do respectably too. Having that baseline in front of me kept the comparison honest.

Training

The moving average climbs, which is the result you want. The raw per-episode reward underneath it is far more interesting: it stays noisy well after the average looks healthy. A DQN that has "solved" CartPole on average can still drop an episode, because ε-greedy exploration keeps injecting random actions and the Q-function is being chased by its own bootstrapped targets.

The gap between the average and the worst case is the whole problem with putting RL on hardware. A control engineer asks for a stability guarantee; a reward curve offers a trend. That tension is most of why I'm reading Ogata alongside this.

What I took from it

  • Exploration vs exploitation is a scheduling problem. The ε decay schedule changed results more than the network architecture did.
  • Replay buffers exist to break correlation. Consecutive frames of a falling pole are almost the same sample; training on them in order is training on one data point repeatedly.
  • A value function is not a controller. It's an estimate of return that a policy is derived from — and the derivation is where the fragility lives.

Where this goes

CartPole is a stepping stone, not a destination. The path I'm on:

  • LunarLander with a DQN — a harder credit-assignment problem with shaped rewards worth analysing.
  • Continuous action spaces, where value-based methods stop being enough.
  • MuJoCo manipulation, which is the actual target: RL that moves a real arm, with control theory keeping it safe.
