A person-aware system across two processors

A camera sees a person; a servo waves and an LED matrix smiles. The interesting part is that perception and actuation run on two different processors that have to stay in step without either one blocking.

Statusresult
Year2026

1The problem

Most beginner vision-plus-hardware projects run inference on a laptop and send commands down a serial cable. That isn't how a robot is built: perception has to live on the machine, and the loop that moves the motors can't stall while a neural network runs.

The UNO Q forces the issue. It carries two processors, a Linux-capable MPU and a conventional microcontroller. Vision belongs on one, real-time actuation on the other, and the two have to agree about the state of the world.

Keeping the bridge as the only interface lets the two sides run at completely different rates. Inference ticks whenever a frame is ready; the control loop ticks continuously regardless.

3The part that mattered

My first firmware used delay() to time the servo sweep. It worked exactly once. While the servo was mid-wave the MCU was asleep, so the matrix wouldn't update and any command that arrived during the gesture was lost. The robot went deaf every time it moved.

Rewrote the firmware as a state machine. Every action is a state with a timestamp, and the main loop only checks whether enough time has elapsed to advance. Nothing blocks, so the MCU stays responsive throughout the gesture.

The same structural lesson recurs in ROS 2 callbacks and any real control system: a loop that blocks is a loop that has stopped controlling.
