Embedded Vision Robotics

Person-aware interactive system on the Arduino UNO Q

A camera sees a person; a servo waves and an LED matrix smiles. The interesting part isn't the behaviour — it's that perception and actuation run on two different processors that have to stay in step without either one blocking.

Year2026

The problem

Most beginner vision-plus-hardware projects run inference on a laptop and send commands down a serial cable. That works, but it isn't how a robot is built — the perception has to live on the machine, and the loop that moves the motors can't stall while a neural network runs.

The Arduino UNO Q is interesting precisely because it forces you to confront this. It carries two processors: a Linux-capable MPU and a conventional microcontroller. Vision belongs on one, real-time actuation on the other, and the two have to agree about the state of the world.

Architecture

I split the system along the natural seam of the hardware and used the Arduino Router Bridge as the only channel between the halves.

MPU · Linux

  • USB webcam capture
  • Video classification brick
  • Person / no-person decision
  • Emits commands
→

Router Bridge

  • Message passing
  • Decouples inference rate from control rate
→

MCU

  • Non-blocking state machine
  • Servo wave gesture
  • LED matrix expression

Keeping the bridge as the single interface means the two sides can run at completely different rates. Inference ticks whenever a frame is ready; the control loop ticks continuously regardless.

The part that actually mattered

My first firmware used delay() to time the servo sweep. It worked exactly once. While the servo was mid-wave the MCU was asleep, so the matrix wouldn't update and any command that arrived during the gesture was simply lost — the robot went deaf every time it moved.

Rewrote the firmware as a state machine. Every action becomes a state with a timestamp, and the main loop only ever checks whether enough time has elapsed to advance. Nothing blocks, so the MCU stays responsive to the bridge throughout the entire gesture.

This is the same structural lesson that shows up again in ROS2 callbacks and in any real control system: a loop that blocks is a loop that has stopped controlling. Learning it on a servo that visibly froze made it stick far harder than reading it would have.

What I'd do next

  • Track where the person is, not just whether one exists, and turn the servo toward them — a genuine closed loop rather than a triggered animation.
  • Add hysteresis to the detection signal so a flickering confidence score can't make the servo twitch.
  • Measure end-to-end latency from frame capture to servo command, which I currently only have a qualitative feel for.
